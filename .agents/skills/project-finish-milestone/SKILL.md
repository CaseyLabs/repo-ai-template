---
name: project-finish-milestone
description: Close out a milestone or work item - run checks, independent acceptance review, simplification, and a milestone commit. Use when the user asks to verify, review, wrap up, or finish a milestone, plan, or set of fixes before committing.
---

Finish the current milestone (the one the user names, otherwise the one in progress). Work through every step without asking whether to continue. The milestone's base is the commit it started from.

When index changes are authorized, first run `git add -N` on the milestone's new untracked files so diffs include them. Never read a whole diff: use `git diff --stat`, then `git diff -- <path>` per file. Give reviewers the base revision, not a pasted diff.

1. **Checks.** Run `python3 tools/project-check.py --base "$base"` from the checkout root and compare its plan with the milestone's acceptance criteria; add required commands with `--extra-command` (JSON argv). Then add `--run`. Evidence captured after the last source edit counts; rerun stale evidence. The evidence is deterministic proof, not review or acceptance. Fix failures before moving on.
2. **Review.** Start the acceptance check (step 3), then review the diff for correctness and regressions with an available code-review capability, or directly, disclosing the substitution. A review that returns no findings or verdict is not complete: retry once, then review directly and report the gap.
3. **Acceptance.** Delegate one read-only check to the native `project-acceptance-checker` agent with the criteria quoted verbatim, the changed-file list and the base revision; [the acceptance brief](references/acceptance-checker.md) defines its reply. If that agent is unavailable, use `project-worker` with the same brief and forbid edits; otherwise check directly. Disclose any fallback and never claim a model or effort setting that wasn't applied. If the result is partial, check the remaining criteria yourself.
4. **Fix.** Fix findings that affect correctness or stated requirements; style-only findings are optional. Don't loosen permissions or guardrails because a reviewer suggests it; ask the user. After code fixes, rerun step 1 and the acceptance evidence commands. Record each confirmed finding you don't fix in `ISSUES.md` (stable ID, links, severity, priority, location, failure, closure criteria).
5. **Simplify.** Review the changed code for behavior-preserving simplification, using a simplify capability if available. If it changes code, rerun the checks as in step 4; otherwise report that no change was warranted.
6. **Plan and docs.** Follow [the lifecycle](../../../docs/PROJECT_MANAGEMENT.md#complete-and-stop): reconcile the checkpoint, roadmap status and linked issues; mark done only on proved acceptance; move lasting decisions and evidence to their docs before pruning; record the **Next recommended** line. Move recurring tooling problems from the register into guidance.
7. **Commit.** If commits are prohibited or execution is restricted, leave changes uncommitted and say so. Otherwise make one commit for the milestone, including all fix rounds. Follow `AGENTS.md` for pushing and landing; for authorized landing, preview with `tools/project-land.sh "$branch" --evidence "$evidence"`, then add a reviewed `--title`, `--body-file` and `--execute`. Never bypass hooks or force-push.
8. **Summary.** List every confirmed finding left unfixed with its `ISSUES.md` ID, or state there are none. Then give a short summary: what shipped, deviations, baseline failures, findings fixed or declined, manual checks outstanding, and the recommended next milestone. Tell the user to start a fresh session and resume from the committed roadmap and checkpoint (name its path); don't offer to continue in this session.
